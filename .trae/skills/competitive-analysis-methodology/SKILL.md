# 竞品分析方法论

## Step 1：建立竞品清单
把竞品按"直接程度"分层：
- **Tier 1**：架构/功能高度重叠（GenOffice, A3S Office, ONLYOFFICE）
- **Tier 2**：单一模块专精（Stirling-PDF, bentopdf）
- **Tier 3**：行业标杆（MS 365, WPS, Adobe Acrobat）

## Step 2：功能归因框架
每个竞品的功能按以下维度评估：

| 维度 | 说明 | 绿角犀评分 |
|------|------|-----------|
| **可抄性** | 我们的技术栈能实现吗？纯 JS 能做吗？ | 1-5 |
| **影响力** | 这个功能对用户有多大感知价值？ | 1-5 |
| **工作量** | 实现需要多少人天？ | 估算 |
| **风险** | 会不会破坏现有功能？ | 低/中/高 |
| **依赖** | 需要引入新依赖吗？ | 是/否 |

## Step 3：拆解热门功能的"为什么"
看到竞品有个热门功能（比如 AI 块级编辑），要问：
1. **它解决了谁的什么痛？** （AI 聊天框要复制粘贴，块级编辑直接改）
2. **它的最低可行实现是什么？** （先做"改写选中段落"，以后再加"生成配图"）
3. **它和我们的架构冲突吗？** （我们的 OS.modules 注册机制支持工具栏扩展，OK）
4. **它的依赖链是什么？** （BYOK → AI fetch wrapper → 密钥存储）

## Step 4：产出落地建议
不输出"竞品有 X 功能"，而是输出：
- ✅ **抄这个**：具体到改哪些文件、加什么函数
- 🟡 **参考但改造成适合我们的**：竞品方式 A，我们做方式 B
- 🔴 **不抄**：原因（技术栈不匹配 / 工作量太大 / 用户不敏感）

## Step 5：沉淀 Skill
把竞品学到的模式写成 SKILL.md，方便以后的 Agent 直接用：
- 设计模式（如"AI 不碰字节边界"）
- 技术决策（如"PDFium 按需加载"）
- 避坑指南（如"Alpha 状态的 AI 路由别学"）

## 数据来源
- GitHub trending（每周一扫）
- npm weekly 下载榜
- Product Hunt
- Hacker News / Reddit r/opensource
- 竞品 README / CHANGELOG / Issue 讨论
- 用户论坛的竞品对比帖子
